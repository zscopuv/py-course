### Welcome Back! 🚀

Expert tests specify behavior at useful boundaries. The goal is confidence to change code, not a large count of tests that repeat implementation details.

---

### 1. Test a Rule, Not Its Internals

```python
import unittest

def discount(total: int, member: bool) -> int:
    if total < 0:
        raise ValueError("total cannot be negative")
    return total * 90 // 100 if member else total

class DiscountTests(unittest.TestCase):
    def test_member_gets_ten_percent_discount(self) -> None:
        self.assertEqual(discount(250, member=True), 225)

    def test_negative_total_is_rejected(self) -> None:
        with self.assertRaises(ValueError):
            discount(-1, member=False)

if __name__ == "__main__":
    unittest.main()
```

The tests name the public rule and boundary. They can survive a refactor from `if` statements to a rule table.

### 2. Use Fakes Before Mocks

```python
class FakeSender:
    def __init__(self) -> None:
        self.sent: list[str] = []

    def send(self, message: str) -> None:
        self.sent.append(message)

def notify(sender: FakeSender, message: str) -> None:
    sender.send(message)

sender = FakeSender()
notify(sender, "ready")
print(sender.sent)
```

A small fake has observable behavior and often communicates better than a mock asserting private call choreography.

### 📝 Notes

- Unit tests should be fast and deterministic; put real database/network checks in a separate integration suite.
- Property-based testing generates many inputs and is excellent for invariants such as encode/decode round trips.
- Automate formatting, linting, type checking, tests, and dependency scanning in continuous integration.
